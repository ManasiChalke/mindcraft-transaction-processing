# Transaction Processing Service

A local full-stack transaction-processing application: a FastAPI backend with an
in-memory queue + background worker pool, backed by SQLite, and a React (Vite)
dashboard for submitting transactions and monitoring processing.

Everything runs entirely on your machine. No hosted queues, no external services.

## Overview

A client (the React dashboard, or any HTTP client) submits a transaction to
`POST /transactions`. The API validates the request, stores it, and returns
immediately — the actual balance-affecting work happens asynchronously on a
background worker pool that consumes from an in-memory queue. Clients poll
`GET /transactions/{id}` (the dashboard does this automatically) to see the
transaction move from `RECEIVED` → `PROCESSING` → `SUCCESS`/`FAILED`.

## Features

- `POST /transactions`, `GET /transactions/{id}`, `GET /customers/{id}/balance`,
  `GET /customers/{id}/transactions` (paginated), `GET /health`.
- Asynchronous background processing via a local `queue.Queue` + a small pool
  of worker threads (no Kafka/RabbitMQ/SQS/Redis).
- Idempotent submission: resubmitting the same `transaction_id` never applies
  a transaction twice, whether it's already finished or still processing.
- Per-customer locking + a single committed DB transaction so concurrent
  debits against the same customer can never corrupt the balance.
- Limited retry (`MAX_RETRIES = 3`) for simulated transient failures; business
  failures (bad amount, bad type, insufficient balance) fail immediately and
  are never retried.
- `processing_attempts` and `failure_reason` are recorded on every transaction.
- React dashboard: submit form, live balance, paginated transaction history,
  loading/error states.
- 15 backend pytest tests + 4 frontend vitest tests, all passing.

## Architecture

```
React (Vite)  →  FastAPI (Uvicorn)  →  queue.Queue (in-memory)  →  Worker threads  →  SQLite
                        │                                                │
                        └────────────── shared DB session factory ───────┘
```

See [ARCHITECTURE.md](ARCHITECTURE.md) for the full explanation of state
transitions, concurrency protection, idempotency and retry design.

## Tech Stack

- **Backend:** Python 3.12, FastAPI, SQLAlchemy, Uvicorn, pytest, httpx
- **Database:** SQLite (file-based, `backend/transactions.db`)
- **Queue/Workers:** Python standard library `queue.Queue` + `threading`
- **Frontend:** React 18, Vite, Vitest, React Testing Library

## Prerequisites

- Python 3.10+ (tested with 3.12)
- Node.js 18+ (tested with 20.17) and npm
- No database server, no Docker, no external services required

## Installation & Setup

### Backend setup

```bash
cd backend
python -m venv venv

# Windows
venv\Scripts\activate
# macOS/Linux
source venv/bin/activate

pip install -r requirements.txt
```

### Database setup

Nothing to do manually — on startup the backend creates `transactions.db`
(SQLite) if it doesn't exist, creates the `customers` and `transactions`
tables, and seeds two demo customers:

| customer_id | balance | currency |
|---|---|---|
| CUST001 | 10000 | INR |
| CUST002 | 5000  | INR |

### Frontend setup

```bash
cd frontend
npm install
```

`frontend/.env` already contains `VITE_API_BASE_URL=http://localhost:8000`.

## Running the Application

**Terminal 1 — backend:**

```bash
cd backend
venv\Scripts\activate        # or: source venv/bin/activate
uvicorn app.main:app --reload --port 8000
```

Backend runs at `http://localhost:8000`. Interactive API docs (Swagger UI) at
`http://localhost:8000/docs`.

**Terminal 2 — frontend:**

```bash
cd frontend
npm run dev
```

Dashboard runs at `http://localhost:5173`.

## API Documentation

Full interactive docs (with request/response schemas) are auto-generated by
FastAPI at `GET /docs` (Swagger) and `GET /redoc` once the backend is running.

### `POST /transactions`

Accepts a transaction and initiates background processing. Returns `201`
immediately with status `RECEIVED` (or `FAILED` for basic validation errors,
or the pre-existing record if `transaction_id` was already submitted).

```bash
curl -X POST http://localhost:8000/transactions \
  -H "Content-Type: application/json" \
  -d '{"transaction_id":"TXN1001","customer_id":"CUST001","amount":500,"currency":"INR","type":"DEBIT"}'
```

```json
{
  "transaction_id": "TXN1001",
  "customer_id": "CUST001",
  "amount": 500.0,
  "currency": "INR",
  "type": "DEBIT",
  "status": "RECEIVED",
  "failure_reason": null,
  "processing_attempts": 0,
  "created_at": "2026-09-22T08:52:26.155403",
  "updated_at": "2026-09-22T08:52:26.155403"
}
```

Poll `GET /transactions/TXN1001` a moment later to see `status: "SUCCESS"`.

### `GET /transactions/{transaction_id}`

```bash
curl http://localhost:8000/transactions/TXN1001
```

Returns `404` if the transaction doesn't exist.

## Concurrency Approach

Every transaction is processed by a worker thread while holding a
**per-customer `threading.Lock`** (created lazily, one per `customer_id`).
The balance is re-read, checked, and written back to SQLite inside a single
committed transaction *while the lock is held*, so two threads can never
interleave a read-check-write sequence for the same customer. Different
customers process fully in parallel (separate locks). See
[ARCHITECTURE.md](ARCHITECTURE.md#concurrency-protection) for the full
walk-through and [TESTING.md](TESTING.md) for the concurrency tests that
prove it.

## Idempotency Approach

`transaction_id` is the SQLite primary key. `POST /transactions` first checks
whether a row already exists for that id — if so, it returns the existing
record as-is (whatever its current status is), and never re-enqueues or
re-applies it. A `try/except IntegrityError` around the insert also covers
the race where two identical requests land at the same instant and both pass
the existence check before either commits.

## Retry Approach

`MAX_RETRIES = 3`. Only **simulated transient failures** are retried (a
hook point in `service.py`, disabled by default, used by tests to force
failures deterministically); **business-rule failures** (invalid amount,
invalid type, insufficient balance) are never retried — they fail on the
first and only attempt. Every attempt updates `processing_attempts` and
`failure_reason`; a transient failure that exhausts all retries becomes a
terminal `FAILED` with reason `"Max retry attempts exceeded: ..."`.

## Troubleshooting

- **`ModuleNotFoundError` running pytest/uvicorn:** make sure the virtual
  environment is activated (`venv\Scripts\activate` / `source venv/bin/activate`)
  and you're running commands from the `backend/` directory.
- **Frontend can't reach the API / CORS errors:** confirm the backend is
  running on port 8000 and `frontend/.env` has
  `VITE_API_BASE_URL=http://localhost:8000`; restart `npm run dev` after
  editing `.env`.
- **`sqlite3.OperationalError: no such table`:** the DB is created on FastAPI
  startup — this only happens if you import `app.main` without ever starting
  the app (e.g. a stray script). Running `uvicorn` or the test suite handles
  this automatically.
- **Port already in use:** another process is bound to 8000 or 5173; stop it
  or run uvicorn/vite with `--port <other-port>` (and update `.env`
  accordingly for the frontend).
- **Stale data:** delete `backend/transactions.db` and restart the backend to
  reset to the two seeded demo customers.
